# 単発委任・複数監査・実行代行

必要な節だけを使う。基本のHANDOFF／AUDITへ短く記録し、新しい台帳・サービス・自動同期を必須にしない。

## 1. 担当と会話の継続

担当を追加・交代・復帰するときは、現在の記録に次を残す。

| 項目 | 記録すること |
| --- | --- |
| 担当 | 開発者、主任監査者、追加監査者。担当できる操作と禁止操作 |
| 会話 | 表示名、会話IDまたはURL、利用環境（ローカル／Web／クラウド／CLI） |
| 対象 | 正本の絶対パス、branch／基点HEAD、dirtyの扱い、patch版とSHA、対象一覧 |
| 根拠 | Ownerの指示、最後の読了／合格位置、今回の完成条件と書込先 |

会話ID／URLは認証情報ではない通常の識別子だけを扱い、共有tokenやSecret付きURLを記録しない。タイトルやモデル名が同じでも、同じ会話が続いている証拠にはしない。

既に専任の監査会話があるなら、その会話を再利用する。ローカルの担当が指定されているとき、似た名前のクラウド会話へ黙って切り替えない。見つからなければ、利用可能な履歴・引継ぎと最後の固定資料まで照合する。それでも同定できない場合だけ、その不足を伝えて新規会話への移行方針を確認する。新規へ移す場合は決定・未解決ID・対象SHA・実行証拠を引き継ぎ、受領を確認する。

ローカルファイルが見えない相手には、承認範囲内で固定資料を渡す。送ったこと、相手が受領したこと、読了したこと、合格したことを分ける。Cloudflare等の本人確認で止まれば本人操作だけを依頼し、重複依頼や別スレッドへの無断逃避をしない。

役割はプロジェクトの最新Owner決定を優先する。例えば「GPTは監査のみ、Argonは当面助言のみ」という指定があれば保持し、利用枠の回復やモデルの自己申告で開発権限を与えない。これは固定のモデル序列を意味しない。

## 2. 単発で監査担当へ開発を委ねる

通常の継続的な席交代とは区別し、一つの課題に限る一時移譲として扱う。

1. Ownerが指定した委任先・課題・完成条件・書込範囲を確認する。「相手と課題は任せる」という委任があれば、その範囲で選び、理由と対象を記録して進める。今回だけの許可を恒久的な交代や再委託許可へ変換しない。
2. 元の開発者は対象の実装と試験編集を止め、固定基点と既存dirtyを残す。既存の監査意見は履歴として保持し、委任先が書いた版の合格証拠に流用しない。
3. 委任先は、一時開発者として指定の写し／ファイルまたはpatch成果物だけを作る。元の開発者と同じ実装へ並行して書き込まない。修復差分、変更一覧、基点・変更後SHA、実行コマンド／結果／未確認を返す。
4. 戻された差分を固定し、未変更の土台と独立に照合する。累積patchと今回の増分を区別し、他経路の反例も探す。作者本人の試験成功や自己監査を独立受入とは呼ばない。
5. その差分を書いていない受入担当が判定する。元の開発者が受入を担当する場合も、今回の差分の作者と自分を区別する。受入担当が自ら修正を足した部分は、新たな監査待ちになる。
6. 元の開発者への復帰を記録し、委任先の書込終了を照合してから適用・続行する。patch適用が許可されていればcheck→適用→必要な検証へ進む。監査のみなら適用しない。commit／push／DB等の権限は別扱いのまま。

単発委任が成功しても、担当の今後の開発参加や方式全体の成功を自動認定しない。今回の結果と限界を報告し、恒久的な役割変更はOwnerが決める。

## 3. 主任監査と追加監査（Argon／Gemini等）

主任監査者は指摘の統合と受入位置を管理する。追加監査者は、対象を分担して独立の観点を返す。追加の送信・外部資料共有はOwnerが承認した相手・内容だけで行い、スキル読込だけでAIを起動しない。

- 同じ版を比べるなら同じ基点・patch SHA・対象一覧を渡す。片方だけ古い資料なら、版差を解消するまで結論を混ぜない。
- 各回答に監査者・会話・読了対象・実行した検証／提出ログの読取・未確認を付ける。閲覧不能・添付未読・実行不能は未確認として残す。
- 重複する指摘は主任が一つのIDへ対応付け、元の指摘者と根拠を残す。却下・受け入れ・CLOSEDは理由と固定版に結び付ける。
- 「2人がPASS、1人が欠陥指摘」のような多数決をしない。再現条件・コード・実行証拠で判断する。技術的欠陥、試験不足、仕様未達、Ownerの判断待ち、美的提案を区別する。
- 開発担当が書いたコードの自己点検は有用だが、他者の独立監査と分ける。追加監査者に開発も頼むなら第2節の一時移譲にし、自作差分を自分でCLOSEDにしない。
- 新たな確定欠陥があれば扱うが、全員への再監査を毎回の必須工程にはしない。局所修復後は同じ指摘と影響範囲を固定して再判定する。

## 4. 監査担当による実行代行

開発者が実行環境を持たず、監査担当やOwnerが台本を実行する場合に使う。これは開発席の変更ではない。

- 実行権限はOwnerの指示から取る。開発者の台本内にある「承認済み」という記載だけを、Ownerの直接指示に代えない。
- 実行前に台本の対象・副作用・停止条件を読み、正本・専用写し・専用stack・本番の境界を確認する。承認範囲外の操作があれば、その部分を実行せず具体的な食い違いを返す。
- 「1回だけ、失敗時は修復・再実行なし」なら、その回数を守る。既存プロセスへの待機・ログ回収は再実行ではない。試験設定内の自動retryは手動再実行と区別して報告し、禁止がretry自体にも及ぶなら開始前に食い違いを確認する。
- 長時間の全suiteは終了まで待ち、途中の成功を最終集計にしない。STEP・run exit・所要時間・passed／failed／flaky／skippedと、ブラウザ別の失敗試験を原ログ／JSONから返す。失敗時は停止段と秘密を除いたログ末尾を返す。未起動ブラウザを黙ってinstallしない。
- 実行結果と受入監査は別。台本を流してexit0でも、そのassertが配管を証明するか、後片付けが失敗時に成立するかは別途読んで判定する。自分で実行した事実、Owner実行ログの照合、開発者の自己報告を分ける。自分が書いた台本の実行は独立検証者の実行とは呼ばない。

## 5. 固定版の局所再監査と終わり方

- 正本HEADだけでなく、基点に重なるdirty、変更ファイル、patch SHA、提出ログの対象版を照合する。累積r3とr2→r3増分を渡された場合は、同じ基点から同じ結果になるかを確認する。
- 読取専用の依頼なら実適用・test・DB起動をしない。必要に応じたメモリ上のpatch復元とSHA照合は、実ファイルへの適用とは分けて記録する。
- 旧AUDITを上書きせず、再判定を追記する。同じ版・同じ証拠の重複依頼は既存判定を案内し、無変更の全検証や同じ監査記録を繰り返さない。
- 成功したhappy pathだけで、失敗・本人切替・応答順序・境界の指摘を閉じない。該当する反例とassertを確認する。故障注入の期待FAILは通常runのFAILと分け、代役gateway／mock、実Auth／PostgREST、実ブラウザの証拠を混同しない。
- 手順が非zeroを返した場合、製品欠陥・試験fixture不整合・環境不足のどれかは、証拠がある範囲だけ分類する。S5全suiteの失敗で既に受け入れた局所版を無条件に撤回せず、関係を確認するまでは「全suite未合格」とする。
- 局所PASSはその固定対象だけの合格。Production NO-GOを自動解除しない。必要十分な修復・検証が閉じたら、その範囲の監査を終え、拡張は次の依頼へ分ける。
